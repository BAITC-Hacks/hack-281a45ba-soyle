# Контракт помощника подготовки задачи

Помощник работает через серверный `POST /api/ai` в два этапа: `questions` задаёт вопросы, `card` собирает карточку из предоставленных сведений. Клиентские функции — `analyzeTask(description, fields)` и `generateTaskCard(description, fields, answers)` в [src/ai.ts](../src/ai.ts). Обработчик и адаптер OpenAI находятся в [server/api.ts](../server/api.ts); middleware подключён к Vite dev и preview.

Режим задаёт сервер: `mock` использует локальные правила без обращения к языковой модели, `openai` вызывает OpenAI Responses API. Оба режима используют один контракт. Ошибка OpenAI не приводит к автоматическому переходу в mock. Искусственной задержки в mock нет; браузеру всё равно нужен работающий сервер приложения.

## Запрос

Нужен `Content-Type: application/json`. Все свойства ниже обязательны, неизвестные свойства отвергаются.

```ts
type FieldKey =
  | 'title' | 'topic' | 'context' | 'need' | 'users' | 'data'
  | 'constraints' | 'result' | 'success' | 'contact' | 'interaction'

type CardKey =
  | 'title' | 'context' | 'need' | 'users' | 'data' | 'constraints'
  | 'expected_result' | 'success_criteria' | 'contact' | 'interaction_format'

type Answer = {
  id: string        // q1…q10, уникален в запросе
  field: CardKey
  question: string  // текст вопроса, не источник фактов
  answer: string    // ответ пользователя; пустая строка допустима
}

type AIRequest = {
  stage: 'questions' | 'card'
  description: string
  fields: Record<FieldKey, string> // все 11 ключей, пустые строки допустимы
  answers: Answer[]               // на этапе questions только []
}
```

На этапе `card` разрешено до 10 ответов. Идентификаторы должны быть уникальными; несколько ответов могут относиться к одному полю. `mode` в запрос не входит: клиент не выбирает провайдера.

## Ответы

```ts
type AIMode = 'mock' | 'openai'

type AnalysisResult = {
  stage: 'questions'
  mode: AIMode
  summary: string
  questions: Array<{
    id: string // q1…q10, уникален в ответе
    field: CardKey
    question: string
    hint: string
    example: string // иллюстрация, не факт пользователя
  }>
  missing_information: CardKey[]
}

type CardResult = {
  stage: 'card'
  mode: AIMode
  card: Record<CardKey, string | null> // все 10 ключей обязательны
  missing_information: CardKey[]
}
```

`validateAnalysis` и JSON-схема допускают **3–10 вопросов**; промпт просит **3–5**, mock формирует **3–5**. `summary`, `question`, `hint` и `example` должны содержать видимый текст. Уникальность требуется для идентификаторов, но не для полей вопросов.

У неизвестных полей карточки значение `null`. Валидатор также приводит строки без видимого текста к `null`. На этапе `card` список `missing_information` обязан точно соответствовать полям с `null`; порядок несущественен, повторы запрещены. На этапе `questions` список отражает отсутствующие сведения и не обязан совпадать с полями всех вопросов: дополнительные вопросы могут уточнять уже заполненное поле.

Валидаторы требуют точный набор свойств на каждом уровне, проверяют режим, этап, идентификаторы, ключи, строки и ограничения длины. Ответ проверяется на сервере и повторно на клиенте; повреждённая карточка не применяется частично. Сервер присваивает `mode: 'openai'` ответу провайдера сам: модель возвращает остальные свойства по строгой JSON-схеме.

Преобразование `cardToFields` сохраняет совместимость с моделью приложения:

| Поле AI-карточки | Поле задачи |
| --- | --- |
| `expected_result` | `result` |
| `success_criteria` | `success` |
| `interaction_format` | `interaction` |
| Остальные ключи | То же имя |

`topic` не входит в AI-карточку. Это отдельное редактируемое поле каталога; редактор сохраняет выбранную тему при применении результата.

## Источники сведений и ручные правки

В mock узкие правила извлекают дословные фрагменты описания: строки с метками вроде `Данные:` и предложения с распознаваемыми формулировками. При отсутствии явного названия используется короткий фрагмент первого немаркированного предложения, максимум 160 символов. Нераспознанные сведения остаются неизвестными. Уже заполненные поля имеют приоритет над извлечением; ответы дополняют соответствующее поле отдельной строкой без дублирования одинаковой строки. Ответы вроде «не знаю» и «уточняется» не становятся фактами карточки. Переполнение поля после объединения вызывает ошибку, без обрезки пользовательских сведений.

Mock выбирает до пяти вопросов по отсутствующим полям в порядке: пользователи, данные, потребность, критерии успеха, контекст, ограничения, результат, взаимодействие, контакт, название. Если вопросов меньше трёх, добавляет вопросы о дополнительных деталях. Формулировки и примеры зависят от темы: сначала учитывается явно выбранная тема, затем описание и контекст. Распознанная отрасль сама по себе не заполняет поле.

Для OpenAI `AI_PROMPT` требует использовать только описание, текущие текстовые поля и `answers[].answer`. Вопросы, подсказки и примеры не считаются фактами. `assertGroundedCard` дополнительно проверяет результат:

- Каждое непустое ручное поле должно целиком сохраниться в соответствующем поле результата после нормализации текста.
- Каждая непустая строка результата должна быть фрагментом хотя бы одного разрешённого источника. Невидимые форматирующие символы и различия в пробелах нормализуются.
- Добавленные факты или замена ручного поля отклоняются с HTTP 502. Перефразирование также может быть отклонено: контракт рассчитан на извлечение текста.

Эта проверка устанавливает связь с исходным текстом, но не проверяет достоверность сведений или правильность их распределения по полям. Автор проверяет и подтверждает карточку перед публикацией.

Редактор хранит ответы отдельно от полей. После успешной генерации отмечает их применёнными; при повторной генерации неизменённые применённые ответы передаются пустыми, чтобы не восстановить сведения, которые автор затем исправил вручную. Изменённый ответ дополняет текущее поле; для замены старых сведений нужно отредактировать карточку. Новые неприменённые ответы блокируют подтверждение и сохранение задачи до формирования карточки; текущий черновик можно скачать.

Примеры из `getAnswerExample` — только подсказки: они не копируются автоматически, не подтверждают поля и не повышают рейтинг. Изменение исходного описания не заменяет заполненный контекст автоматически; редактор снимает его подтверждение и просит проверить. После генерации все подтверждения карточки сбрасываются. Ошибки запроса сохраняют введённые данные в форме, без обещания их записи в постоянное хранилище.

## Ограничения и ошибки

| Ограничение | Значение |
| --- | --- |
| Описание | От 10 символов после `normalizeVisibleText`, исходная длина до 20 000 |
| Название и тема в `fields`, название карточки и ответ для `title` | До 160 символов |
| Остальные текстовые значения | До 20 000 символов |
| Сериализованный AI-запрос | До 200 000 символов по `JSON.stringify(...).length` |
| HTTP-тело запроса к серверу | До 512 КиБ |
| Ответ провайдера, включая оболочку Responses API | До 512 КиБ |
| JSON-ответ помощника на клиенте | До 300 000 символов, проверка после чтения тела |
| Ожидание провайдера на сервере | 25 секунд, затем отмена запроса |
| Ожидание `/api/ai` на клиенте | 30 секунд, затем отмена запроса |

Строковые пределы проверяются через JavaScript `string.length`. Внешний запрос использует `store: false`, `max_output_tokens: 6000` и строгую `json_schema` для выбранного этапа. Сервер принимает только завершённый ответ провайдера со статусом `completed`, извлекает `output_text`, затем проверяет JSON и контракт.

Ошибки API имеют вид `{ "error": "Сообщение на русском" }`. Основные статусы: 400 — неверный ввод, 413 — размер HTTP-тела, 415 — тип содержимого, 502 — сбой провайдера или отклонённый ответ, 503 — конфигурация, ключ, доступ, модель или лимит провайдера, 504 — тайм-аут. Неправильный HTTP-метод возвращает 405. Запрос с заголовком `Origin` другого host или недопустимой схемой отклоняется с 403. Сырой ответ провайдера и ключ в ошибках клиенту не передаются; HTML от прокси не используется как текст ошибки интерфейса.

## Серверная конфигурация

Для mock `.env` не нужен. Настройки из `.env.example` загружаются сервером в [vite.config.ts](../vite.config.ts):

```dotenv
AI_MODE=mock
OPENAI_API_KEY=
OPENAI_MODEL=gpt-4o-mini
OPENAI_ORG_ID=
OPENAI_PROJECT_ID=
```

Для настоящего вызова нужно установить `AI_MODE=openai`, заполнить отдельный API-ключ и перезапустить сервер. Наличие ключа само по себе не меняет режим. `OPENAI_ORG_ID` и `OPENAI_PROJECT_ID` необязательны и передаются отдельными заголовками; строка вида `org-…` — идентификатор организации, а не ключ. Сервер отклоняет идентификатор организации или проекта в `OPENAI_API_KEY`, пробелы внутри ключа, пустую модель и переносы строк в идентификаторах.

`.env` исключён из Git. Ключу нельзя добавлять префикс `VITE_`: он нужен только серверу. Реальные ключи и идентификаторы не должны попадать в отслеживаемые примеры или клиентский код.

`GET /api/health` возвращает HTTP 200 и `{ ai: { mode, configured, message } }`, где `mode` — `mock`, `openai` или `invalid`. Это проверка локальной конфигурации: она **не вызывает OpenAI и не проверяет действительность ключа или доступ к модели**. Секретные значения в статус не включаются. Реальный доступ проверяется при запросе `/api/ai`.

## Подтверждение и публикация

AI не рассчитывает рейтинг, не подтверждает и не публикует задачу. `POST /api/tasks/confirm` принимает `{ fields }`, подтверждает все непустые поля и возвращает `{ confirmedFields, rating }`. Пустая карточка отклоняется.

`POST /api/tasks/publish` принимает `{ fields, confirmedFields }`, проверяет название, тему и подтверждение каждого заполненного поля, затем возвращает `{ rating }`. Рейтинг рассчитывается общей детерминированной функцией `getRating`. Эти endpoints проверяют поля и возвращают результат; сохранение самой задачи выполняется отдельно в браузере.

## Проверки

```sh
npm test -- src/ai.test.ts server/api.test.ts
npm run test:e2e
```

Модульные проверки покрывают контракты, извлечение фактов, примеры, отсутствие выдуманных сведений, сохранение ручных полей, пределы, ошибки и тайм-ауты. Тесты серверного OpenAI-адаптера подменяют провайдер и не требуют действительного ключа. Playwright проверяет полный путь через отдельный локальный сервер в `AI_MODE=mock`, включая редактирование, подтверждение, публикацию и повторную работу с ответами.
