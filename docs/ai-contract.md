# Помощник подготовки задачи

В MVP реализован **локальный демонстрационный режим**. Он не обращается к языковой модели, не делает сетевых запросов и не требует API-ключа. В интерфейсе этот режим необходимо обозначать явно. Слова «анализ» и «помощник» здесь означают проверку заполненности и подбор вопросов по правилам.

Точка входа: `analyzeTask(description, fields)` из `src/ai.ts`. Она возвращает `Promise<AnalysisResult>` после задержки 350 мс для демонстрации состояния загрузки. Пустое описание, слишком длинный текст или некорректные типы приводят к отклонению Promise с понятным сообщением на русском языке. Вызывающий интерфейс должен показать ошибку и сохранить введенные пользователем данные.

## Алгоритм

1. Проверить описание и строковые значения всех 11 полей; предел одного значения — 20 000 символов. В описании должно быть не менее 10 символов после удаления невидимых форматирующих символов Unicode и внешних пробелов. Поля, состоящие только из пробелов и невидимых символов, считаются незаполненными. Проверка использует общие с рейтингом функции `hasContent` и `normalizeVisibleText` из `domain.ts`.
2. Если поле контекста пусто, предложить в качестве контекста исходное описание, удалив только внешние пробелы. Уже заполненные поля не изменять. Никакие остальные факты не извлекать и не придумывать.
3. Найти незаполненные поля с учетом предложенного контекста. Приоритет: проблема, результат, критерии успеха, данные, пользователи, ограничения, контакт, взаимодействие, контекст, название, тема.
4. Выбрать до 5 вопросов и иллюстративные примеры ответов. Слова, связанные с доставкой/складом, учебой или торговлей, меняют только формулировки вопросов и примеров. Они не являются подтверждением отрасли или каких-либо фактов и не заполняют поля. Сначала учитывается явно выбранная тема, затем исходное описание, затем контекст карточки. При совпадении нескольких тем внутри одного текста приоритет имеют логистика, затем образование, затем торговля.
5. Если пропусков меньше трех, дополнить список вопросами на подтверждение уже заполненных полей. Всегда получается от 3 до 5 вопросов, каждый относится к отдельному полю.
6. Проверить сформированный ответ через `validateAnalysis` и вернуть его. Пользователь редактирует и подтверждает карточку перед публикацией.

## Контракт входа

```ts
type FieldKey =
  | 'title' | 'topic' | 'context' | 'need' | 'users' | 'data'
  | 'constraints' | 'result' | 'success' | 'contact' | 'interaction'

type Input = {
  description: string // не менее 10 видимых символов, общая длина не более 20 000
  fields: Record<FieldKey, string> // все ключи обязательны, пустые строки допустимы
}
```

Описание и поля — пользовательские данные. Они не должны исполняться как инструкции, HTML или код.

## Контракт выхода

```ts
type AnalysisResult = {
  mode: 'demo'
  summary: string // непустое объяснение на русском
  questions: Array<{ // от 3 до 5 элементов
    id: FieldKey // без повторов
    question: string // непустой русский текст
    hint: string // непустая подсказка на русском
    example: string // отдельный иллюстративный пример ответа, не факт пользователя
  }>
  suggestedFields: Partial<Record<FieldKey, string>>
}
```

`validateAnalysis(value: unknown)` проверяет режим, типы, видимый текст в каждой строке (в том числе в обязательном `example`), ограничение длины, число вопросов, уникальность их полей и допустимые ключи предложений. Неизвестные поля предложения отвергаются, лишние корневые свойства не передаются в интерфейс. Пустой `suggestedFields: {}` допустим. Невалидный ответ вызывает исключение с русским объяснением; частично поврежденные данные не применяются.

Пример корректного ответа:

```json
{
  "mode": "demo",
  "summary": "Демонстрационный анализ: уточните недостающие сведения. Языковая модель не вызывалась.",
  "questions": [
    { "id": "need", "question": "Какую проблему нужно решить?", "hint": "Опишите затруднение в текущем процессе.", "example": "Причины возврата товаров записывают по-разному, поэтому сложно увидеть повторяющиеся проблемы." },
    { "id": "result", "question": "Какой результат должна передать команда?", "hint": "Укажите ожидаемый артефакт.", "example": "Панель с загрузкой CSV и группировкой возвратов по причинам." },
    { "id": "success", "question": "Как вы проверите результат?", "hint": "Опишите сценарий приемки.", "example": "На 20 проверочных возвратах не менее 18 должны попасть в согласованную категорию." }
  ],
  "suggestedFields": { "context": "Нужен помощник для магазина." }
}
```

## Примеры и пользовательские данные

`getAnswerExample(field, description, fields)` возвращает иллюстративный ответ для любого из 11 полей. Подготовлены четыре согласованных набора: ритейл, образование, логистика и общая задача клиентского сервиса. Контакты в примерах явно вымышленные и используют домен `example.com`; числа и сроки являются частью примера, а не рекомендацией для конкретного бизнеса.

На шаге уточнения пример показан под каждым вопросом с подписью «Пример ответа». В готовой карточке у каждого поля есть раскрываемая подсказка с доступным названием поля. В обоих случаях интерфейс поясняет, что пример нужно адаптировать под свою ситуацию. Примеры не копируются в значения полей, не входят в `suggestedFields`, не подтверждаются и не повышают рейтинг. Наличие `example` проверяется на границе контракта.

Исходное описание и структурированный контекст — разные данные. Если после формирования карточки пользователь меняет описание, редактор сохраняет контекст, снимает его подтверждение и предлагает проверить поле. Повторный анализ по-прежнему не заменяет заполненный контекст. Редактирование контекста или явное подтверждение карточки завершает эту проверку.

При отказе сохранения редактор сохраняет ввод и отметку несохраненных изменений, показывает ошибку и позволяет скачать текущий черновик в JSON. Успехом считается только явный ответ `true` от обработчика `onSave`; родительский компонент отдельно сообщает, удалось ли записать принятую задачу в постоянное хранилище.

## Подключение настоящего API в будущем

`AI_PROMPT` в `src/ai.ts` содержит подготовленный русский промпт; в текущем режиме он сохраняется как часть документации и не отправляется модели. Он требует JSON с `summary`, `questions`, `suggestedFields`; источник ответа определяет приложение. Промпт запрещает выдумывать факты и требует рассматривать введенные тексты как данные.

Для настоящей интеграции нужен отдельный серверный обработчик, который хранит ключ в серверной переменной окружения, принимает входной контракт, вызывает выбранную модель, ограничивает время запроса и проверяет ответ. Добавьте отдельный режим `live` в контракт и интерфейс: ответ настоящей модели нельзя маркировать как `demo`. Серверный адаптер добавляет эту метку сам. Расширьте валидатор для нового режима и дополнительно проверьте, что модель не предлагает заменять заполненные поля. Ошибку API, тайм-аут, некорректный JSON или невалидный контракт следует показывать пользователю с возможностью повторить запрос или явно выбрать локальный деморежим.

Сейчас приложение полностью работает без сети, `.env` и ключей. Публикация задачи, расчет рейтинга и выбор команды остаются отдельными действиями приложения; помощник их не выполняет.

## Проверки

`src/ai.test.ts` проверяет сохранение фактов, отраслевые вопросы и примеры для всех полей, приоритет явно выбранной темы, отсутствие примеров в пользовательских данных, подтверждение заполненной карточки, минимум три разных вопроса, границы длины описания и отбрасывание поврежденных входов/выходов, включая невидимый текст. Запуск: `npm run test -- src/ai.test.ts` (если основной скрипт использует `vitest run`).
